# HustleXP Documentation Alignment Register

**Register version:** 1.1.0  
**Evidence date:** 2026-08-25  
**Classification:** CURRENT EVIDENCE  
**Production effect:** NONE

This register classifies documentation families after adoption of the HustleXP Business and Universal V1 Charter. It preserves evidence while preventing stale material from becoming accidental authority.

## Controlling

| Document | Scope |
| --- | --- |
| `governance/HUSTLEXP_BUSINESS_AND_UNIVERSAL_V1_CHARTER.md` | Company, business, lanes, market cell, categories, Universal V1 target, metrics, money freeze |
| `governance/DECISION_2026-08-25_REGULATED_TRADE_BUSINESSES_ACTIVE_GATED.md` | First-class trade-provider decision, marketplace role, capability gates, economics hypotheses, legal boundary |
| `governance/VERIFIED_TRADE_CREDENTIAL_MATRIX_WASHINGTON.md` | Washington launch verification architecture and initial category evidence matrix |
| `governance/DOCUMENTATION_AUTHORITY_AND_SOURCE_PRECEDENCE.md` | Cross-document precedence and conflict resolution |

## Subordinate implementation references

These may remain useful only within the charter and current repository truth:

- product, frontend, screen, design-system, component, accessibility, messaging, notification, and onboarding specifications;
- backend/API/storage/job/architecture specifications;
- `/OPS`, support, evidence, incident, and runbook material;
- current brand and UX implementation references;
- repository READMEs that accurately describe their repository role.

Subordinate documents must not independently authorize money, deployment, universal availability, licensed-trade assignment, provider eligibility, final pricing, or production capability.

## Current evidence

- exact repository SHAs, CI results, build identities, deployment observations, migrations, incidents, and production configuration readbacks;
- backend current checkpoints and signed evidence records;
- processor correspondence, legal opinions, insurance decisions, and certification receipts when obtained.

Evidence is source-dated and does not become permanent policy.

## Validation material

- fee percentages, provider floors, service timers, first-100 thresholds, liquidity gates, growth targets, and the 12-month target in the charter;
- underwriting planning volumes and hypothetical processor mechanics;
- GTM channel experiments and category economics.

Validation material must be labeled as a target or hypothesis wherever repeated.

## Historical or superseded families

The following are preserved but non-controlling where they conflict with the charter:

- `APP_OVERVIEW.md` and prior product-identity summaries;
- `CURRENT_PHASE.md` and other source-dated launch-readiness claims;
- `FEATURE_FREEZE.md`, `FINISHED_STATE.md`, and fixed-count V1 definitions;
- `specs/01-product/PRODUCT_SPEC.md` v1.6.0;
- `specs/01-product/UNIT_ECONOMICS.md` when it states permanent prices or legacy payment semantics;
- `BACKEND_STACK_LOCK.md` where it claims Neon, Stripe, or another vendor is company-level permanent authority;
- `PER/*` project-execution records where their authority ladder conflicts with this register;
- files under `_archive/`, `tracking/audits/`, past plans, staging history, and generated audit reports;
- Google Drive roadmaps, build subsets, checklists, and underwriting documents predating the charter;
- repository READMEs containing old slogans, universal/no-category promises, gamification-first positioning, old lifecycle shorthand, or stale implementation counts.

Historical documents may be cited as evidence of what was believed, designed, or observed at the time. They may not authorize current execution.

## Known conflict translations

| Legacy expression | Canonical interpretation |
| --- | --- |
| “Gamified hyperlocal task marketplace” | Managed local-work transaction network; gamification is subordinate experience design |
| “No categories / any request / no waiting” | Wide intake with explicit category, risk, serviceability, and eligibility routing |
| “Escrow funded before task posting” | Task Draft first; processor-neutral Financial Security Event before Work Order and assignment |
| “Stripe is the payment architecture” | Processor-neutral core; specific processor behavior is externally approved adapter policy |
| “Task posted means provider can claim” | Opportunity/interest only until eligibility, conditional acceptance, FSE, materialization, and assignment |
| “Licensed trades are future, referral-only, or permanently free” | First-class `ACTIVE_GATED` managed marketplace lane; referral may be interim, while exact unauthorized payment capabilities remain blocked |
| “Google-verified contractor” | Reputation-qualified prospect plus independently credential-verified trade business |
| “AI auto-prices/assigns/approves” | AI may assist; typed policy and authorized human/system controls decide |
| “Product is launch-ready except legal” | Historical claim; current implementation, release, legal, processor, and production evidence control |
| Static test/table/router counts | Source-dated evidence only; never copied forward as current truth |

## Repository alignment rule

Every active HustleXP repository README should:

1. identify the repository's bounded role;
2. link to the canonical charter;
3. repeat the one-company doctrine accurately;
4. state that documentation does not authorize production deployment or money movement;
5. avoid stale counts and unsupported production-readiness claims;
6. classify legacy or audit content as historical evidence.

## Remaining external evidence

The charter is complete without pretending the following are settled:

- Washington legal role, worker classification, crew/subcontractor, permit, warranty, and licensed-trade decisions;
- insurance and background-screening requirements;
- processor program, categories/MCCs, provider types, Financial Security Event, fees, limits, reserves, losses, adjustments, replacement, settlement, and payout behavior;
- observed customer demand, provider response, service timings, repeat behavior, CM1, CM2, and first-100 cohort results.
